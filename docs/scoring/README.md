# CRM訪問スコアリング

船井総研の「CRM訪問スコアリング機能 実装仕様書」（2026-07-21 版 1.0）を東京新電機様の CRM に入れる。
SalesIQ から入る「訪問」の閲覧ページ URL をルールと照らして、見込み客・担当者（`Contacts`）に点数を足し、
30日訪問が無ければ 25% ずつ減らす。

## 仕様書からの変更（2026-10-18 に決めたこと）

| 仕様書 | 東京新電機様 | 理由 |
|---|---|---|
| 顧客担当者の「顧客タイプ区分名」で対象を絞る | **使わない**。すべてのルールが全員に効く | この組織に該当の項目が無く、今回は要らない |
| スコアリングルールの「属性区分」 | **作らない** | 同上 |
| 主項目（名前） | 「説明」を主項目にする（API 名 `Name`） | ルールの中身が URL だけでは分からないため、必ず書いてもらう |
| 問合せ者・名刺（`Leads`）の訪問 | 対象外 | |
| `WebVisitLog`・`IPCompany` | 触らない（インテントセールス用。今は動いていない。削除しない） | |

## CRM に作るもの（API 名はここと `crm/scoring/*.json` だけに書く）

スコアリングルール（新しいモジュール `ScoringRules`）

| 表示名 | API 名 | 種類 | 中身 |
|---|---|---|---|
| 説明 | `Name` | 1行テキスト（主項目） | ルールのメモ（例「FAQ 閲覧」） |
| スコアリング対象 | `Scoring_Target` | 選択リスト | 「閲覧したURLが」だけ |
| 値 | `Match_Value` | 1行テキスト（255文字） | 判定する URL |
| 条件 | `Match_Condition` | 選択リスト | を含むとき／を含まないとき／と等しい／と等しくない |
| 点数 | `Points` | 整数 | 条件が成り立ったときに足す点数 |

見込み客・担当者（`Contacts`）に足す項目

| 表示名 | API 名 | 種類 |
|---|---|---|
| CRM訪問スコア | `CRM_Visit_Score` | 整数 |
| スコア計算済み日時 | `Score_Calculated_At` | 日時 |
| スコア減衰日 | `Score_Decay_Date` | 日付 |
| スコア保有 | `Has_Score` | チェックボックス |

既存の項目・レイアウト・ワークフローは変えない。削除はしない。

- **主項目の表示名が「説明」にならず「スコアリングルール名」になった。** `display_field.field_label` は使われなかった（API 名は `Name`、120文字、必須）。

- 選択リストには Zoho が `-None-` を先頭に足した

| 関数の API 名 | ファイル | カテゴリー・引数 | 呼び出し元 |
|---|---|---|---|

- 仕様書第4・5章のソースの★を、上の API 名に差し替えた。加算関数からは「顧客タイプ区分名」「属性区分」の絞り込みを外した（すべてのルールが全員に効く）。それ以外の処理は仕様書のまま
- 関連リストの API 名 `Visits_Zoho_Livedesk`（Contacts）・`Actions_Performed`（Visits）は、2026-10-18 に `GET /settings/related_lists` で確認した
- `CUTOFF`（稼働開始日時）は `2026-10-18 19:55:00`（2026-10-18 に本稼働。それより後に作られた訪問から加算）。テストで過去に変えたら戻す
- 通知は本稼働（`TEST_MAIL = false`）。東京新電機様の5名（`MAIL_TO_PROD`）に送る
- 2026-10-18 19:57 に、このリポジトリの版を `tsd_crm function-update` で CRM の `add_crm_visit_score` に反映した（以後の更新も同じ方法で送れる）
- 減衰関数は `DRY_RUN = true` で置いている
- **ホットリード通知**（加算関数の STEP5。2026-10-18 に追加）：スコアが100点未満から100点以上に上がったとき（減衰で下がって再び上がったときも）、
  見込み客・担当者の詳細とレコードURL、今回加算したスコアリングルール（説明・条件・点数・一致回数・レコードURL）、一致した閲覧の明細をメールで送る。
  送り先は関数の `MAIL_TO_PROD`。`TEST_MAIL = true` の間は `MAIL_TO_TEST`（r-kanezashi@funaisoken.co.jp）だけに、件名に【テスト】を付けて送る。あわせて既存の項目「ホットリードになった日」（`field19`）に今日の日付を入れる（`SET_HOT_DATE`）。
  メールはスコアの更新に成功した後だけ送る
  - 見込み客・担当者のメールアドレスが `@funaisoken.co.jp`・`@tokyoshindenki.co.jp` の人には通知しない（`EXCLUDE_INTERNAL = true`。社内のアドレスでテストするときだけ `false`）。スコアと「ホットリードになった日」は更新する
  - ★既存のワークフロー「ホットリード時_メール通知、項目更新」（`13772000001479139`）も、SalesIQ の訪問スコア `Visitor_Score` が50以上になったとき（最初の1回だけ）に
    同じ `field19` を更新し、メールを送っている。この関数はワークフローを発火させない更新なので、そのワークフローは動かさない（触っていない）。
    両方残し、どちらでも「ホットリードになった日」を入れる（2026-10-18 にユーザーが決定）

## 認証情報（構築用）

`docs/setup.md` の手順1・3と同じやり方で、認可コードを次のスコープで発行し直す（スコープは後から足せない）。

```
ZohoCRM.org.READ,ZohoCRM.users.READ,ZohoCRM.modules.ALL,ZohoCRM.coql.READ,ZohoCRM.settings.modules.ALL,ZohoCRM.settings.fields.ALL,ZohoCRM.settings.layouts.ALL,ZohoCRM.settings.profiles.READ,ZohoCRM.settings.related_lists.READ,ZohoCRM.settings.functions.ALL,ZohoCRM.settings.workflow_rules.READ,ZohoCRM.settings.automation_actions.READ
```

今の読み取り用の権限をすべて含むので、工数ダッシュボードの突き合わせ（`scripts/verify_worklog_totals.py`）もそのまま動く。
